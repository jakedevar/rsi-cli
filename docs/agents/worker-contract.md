# Worker contract reference

The launch preamble stays brief because every leaf worker pays its prompt cost. `AGENTS.md` holds canonical repository rules. The including command supplies role, task, return schema, and any tighter limits. A parentless session directly addressed by the human may answer plainly; do not infer that status from a title or missing schema.

## Source ancestry

Start from your allocated source on the assigned sandbox branch and preserve
its ancestry. Merge `origin/rolling` when needed; never rebase a source stack.
The queue's lander integrates `rolling`. Custody and pending verification wakes
require the allocated source to remain an ancestor of your head.

## Verification bounds

Desktop workers, including satellite workers on macOS and Windows, run
`cargo test --locked --manifest-path desktop/src-tauri/Cargo.toml`; an unlocked
test can silently repair a stale lock and hide a merge-queue failure. Dependency
changes in the desktop's path dependencies (including rsi-common and rsi-graph)
must refresh and commit `desktop/src-tauri/Cargo.lock` in the same source as the
root lock. The shared desktop lane refuses a stale lock as `desktop_lock_stale`
and names the repair: `cargo update --workspace --manifest-path desktop/src-tauri/Cargo.toml`.

Acceptance is a green `scoped_test` receipt whose `receipt_head` equals the exact final committed HEAD. Run one `scoped_test` per final head (`AgentSubmitJob {"kind":"test","wake":"none","params":{"scoped_test":{"base":"origin/rolling"}}}`, then ONE `AgentScheduleWake {"mode":"when","message":"scoped_test finished: read the receipt","when":{"jobs_terminal":["<job id>"]}}`; `message` is required, a call without it is refused `invalid_input`); it derives the touched-module filters itself, and the merge queue derives the landing filters, so do not run `scripts/check-touched-shards` by hand. After a red run, fix the cause, commit, push, and run exactly ONE more `scoped_test`. Never loop or retry the same head; if the second run is still red, hand off with the reds named instead of starting a third. For compile errors while you work, submit a `build` job with `command:"check"` and `package` (`AgentSubmitJob {"kind":"build","params":{"command":"check","package":"<crate>"}}`): it rides the governor's separate check lane (#2430) instead of queuing behind full builds and test runs, so use it before `scoped_test` rather than spending a scoped_test round on a type error. Compile feedback is optional and only when the launch brief permits it: a brief that sets a verification policy (`scoped_only`) or forbids a broad build wins, and a prose-only, docs-only or source-only change needs none. A `check` job passes `--keep-going`, so cargo does not stop at the first failing crate; when more than one crate may be affected (a shared type or signature change), you may submit one `{"kind":"build","params":{"command":"check","workspace":true,"all_targets":true}}` job instead of one single-crate job per crate: it reports every crate's errors, test targets included, in one round (#2516). To verify shard features (`--no-default-features --features test-shard-X`) never start your own cargo unit: submit one `{"kind":"build","params":{"command":"test_no_run","package":"rsid","shards":["store-01","other-02"]}}` job (#2692). It builds the shards in `rsi-build.slice`, cleans the package between them so the target stays small, and its receipt names each shard's exit code and warning counts (judged by the #1897 gate). For a new runtime or schema assertion you are unsure of, you may first submit ONE exact package job per touched crate (`{"kind":"test","params":{"package":"<crate>","lib_only":true,"exact":true,"filters":["<module>::tests::<name>"]}}`, full module path): optional early feedback on the working tree, not committed bytes, so never acceptance. When `filters` is non-empty, it exits 0 and its whole log proves libtest ran no test (0 passed and 0 failed in every test binary), it settles `failed` `job_filter_matched_no_tests` with exit_code 0 kept; a custom harness or unreadable log keeps the ordinary result. Do not use it for `rsid-store` migration suites (disk-backed scratch, slow); the final committed `scoped_test` still derives the acceptance scope. A `scoped_test` has a bounded 60-minute default (or a higher operator test default, capped at 180); allow healthy progress inside its admitted budget rather than stopping it at 20 or 30 minutes. Inspect stalled, over-broad or unbounded work and host CPU pressure; cancel your own runaway job with `AgentCancelJob` and report its command, elapsed time and log. Other runs stop at twice their expected time or the brief's deadline, whichever comes first (30 minutes if neither is known). An explicit brief deadline still applies to `scoped_test`. Stop only processes or units you started; `AgentHalt` stops a provider session, not a detached job. Do not repeatedly restart timed-out runs or use long sleep-poll loops. The suggested filters are bounded and exact (named tests, not module prefixes); a receipt with `broad: true` names a filter that may not finish in a worker's budget, so run it in parts or say so in the handoff (usage text in the script).

Read the receipt's `merges_cleanly_onto_rolling` (#348): `scripts/scoped-test` runs a fetch-free `git merge-tree --write-tree origin/rolling HEAD` at the end and records `merges_cleanly_onto_rolling` (`true`, `false`, or `null` with `merge_check_reason` when git could not say) and, when false, `conflict_paths` (the first 32, `conflict_paths_total` the full count). It is informational and never changes the run's verdict, so a green run can still name a commit that no longer merges. When your receipt shows `false`, merge `origin/rolling` into your branch (no rebase), resolve the named paths, commit and push; verify the new head within the two-run limit above, or hand off the remaining blocker. `AgentCheckLandingCandidate` reports the same fact (and a fresh check against the current `origin/rolling`) as `candidate_conflicts_with_rolling`, and the worker roster's job summary carries it.

## Python verification

Python suites in `scripts/tests` and `tools/tests` are stdlib `unittest` suites: run them with `python3 -m unittest -v <test file>` (or `discover -s scripts/tests -p <file>`). A brief never names `pytest` as a required runner; no RSI host installs it. `scripts/python-test-gate.py` still plans the optional pytest adapter for a function-style tools suite that does not import `unittest`, and `scripts/scoped-test` preflights every planned runner (`runner_status`). A missing interpreter or module is the typed `runner_unavailable`: the `python` receipt entry carries `status`, `runner`, `python`, `test_file`, `reason` and `executed_tests: 0`, the job is red, and no other runner is substituted. A genuine failure is `status: failed` with the runner's own exit code, and a unittest run that executes 0 tests is `no_tests_executed`, also red. Report `runner_unavailable` as the prerequisite it is; do not install packages, and do not call a zero-test run green. An explicit command from the task stays authoritative: run it, and report its failure verbatim.

## Fixture Git

A fixture or reproduction repository is never reached by `cd <dir> && git ...` or by a bare `git` whose working directory is implied. If the `mkdir`, `mktemp` or `cd` fails, the shell carries on and Git acts on the worktree you are standing in, which in a sandbox is your assigned branch (hard rule 2; #2291 made two junk commits and a `reset --mixed` that way). Instead:

- Create the directory, check that it exists and is outside your sandbox root, then run every Git command as `git -C <absolute dir> ...` (or with explicit `GIT_DIR` and `GIT_WORK_TREE`). Never reset, check out, switch or branch-change the assigned worktree to repair a mistake; stop and report.
- Python scripts and tests use `scripts/scratch_git.py`: `scratch_git(dir, *args)` requires an absolute, existing directory whose resolved path (symlinks followed) is outside this checkout, the worktree around the current directory (found the way Git finds it, so a `GIT_CEILING_DIRECTORIES` entry above the current directory ends the walk: a job unit sets one at its private `TMPDIR`, which lies under the operator's home repository, #2612) and any `GIT_DIR`/`GIT_WORK_TREE`, runs `git -C <resolved dir>` with every repository-location variable removed and a `GIT_CEILING_DIRECTORIES` above the scratch directory, and raises `ScratchGitError` before Git starts otherwise. There is no exemption: a sandbox's own `TMPDIR` (`target/.rsi-tmp`) is inside the sandbox and is rejected. Fixtures allocate with `scratch_tempdir(prefix)`, which picks a disk-backed host temporary directory outside every protected root (`/var/tmp`, `/tmp`, ...) without changing `TMPDIR` or `tempfile.tempdir`. Tests that need a fake "assigned" repository build it there; none exercises a denied mutation in the live sandbox.
- The custody scan (`rsi_common::custody_scan`, shared by the CLI hook and the Harness tools, #2571) refuses a `cd`/`pushd` to a scratch or temporary location (a `/tmp`-style path, `$TMPDIR`, `mktemp`, a variable holding one) followed in the same command line by a repository-changing Git command (`commit`, `add`, `reset`, `update-ref`, `branch <name>`, `tag <name>`, `config` writes, ...) that is not pinned by a literal absolute path: `-C /abs`, or both `--git-dir /abs` and `--work-tree /abs` (or `GIT_DIR=/abs GIT_WORK_TREE=/abs` written in front of that same command). A variable, `$(...)`, `~` or relative path is not a pin because it may be empty, an earlier `export GIT_DIR=` pins nothing later, and a later `cd` to a sandbox path does not clear the risk. Reads, pinned commands, ordinary assigned-branch `commit`/`fetch`/`merge`/`push` and scratch words inside quoted messages are not refused. Limits: it reads one command line, not earlier tool calls; it does not expand `${VAR}` (brace splitting), follow functions, or know what a variable holds, so a pin must be a literal path (`git -C "$dir"` after a scratch `cd` is refused). The guard is a cooperative guard rail, not a security boundary.

## Evidence and return

**Branch publication before handoff.** Push the committed HEAD to your assigned
sandbox branch with `git push origin HEAD:refs/heads/<branch>`, never `main` or
`rolling`, and never force. If the push fails for any reason other than a
non-fast-forward rejection (including `fatal error in commit_refs`), retry the
same non-force push exactly once. A non-fast-forward rejection requires fetching,
inspecting and integrating the remote ancestry before pushing again; do not
blindly retry it.

After a successful initial push or retry, run
`git ls-remote origin refs/heads/<branch>` and require its returned SHA to equal
`git rev-parse HEAD` before reporting that SHA as published. If the retry fails,
the remote read fails, the branch is missing or the SHAs differ, report the
publication blocker and observed errors in the handoff; do not claim publication
succeeded.

`[observed]` means executed or inspected in this pass; cite the actual result. `[source]` means extracted from an authoritative source with an exact location or reproducible extraction. `[inferred]` means reasoned but unverified. Mechanically extract counts, schemas, and field sets. Check the current tool surface before claiming an exact helper or payload shape. Do not use inference as acceptance or success evidence, or call an inference-bearing plan implementation ready without resolving it.

**Model identity.** The daemon prepends an `RSI session identity` line (provider, model, effort) to every launch. Report an author or reviewer model only from that line, never from the model names in the router table, which name routing classes. Leads cite the session row, not a worker's self-report (#597).

**Replay against cited rows (#2221).** When the Issue cites `[observed]` database rows (counts, ids, a stuck population), a green test over rows you built yourself is not acceptance. The handoff's acceptance evidence includes a read-only replay of the new predicate (the SQL, or the store call, as a `SELECT` against the live DB; diagnostics SQL is allowed) over the cited rows, with the matched count before and after the change, for example `matched 0/26 -> 26/26`. Take the row shape from what the daemon writes (read a real row, or the production writer), never from a shape you invented. If the cited rows are unreachable from your sandbox, say so in the handoff and name the check that would settle it; do not claim the outcome. A reviewer of a custody, reclaim or lifecycle fix repeats the replay on the final commit.

A worker's final answer to a master has `PIPELINE HANDOFF — <STAGE>:` on the first nonblank line (em dash, uppercase stage, trailing colon). Use the including command's stage, body schema and per-field caps. Issue implementation workers use `PIPELINE HANDOFF — IMPLEMENTATION:`; reviewers use `PIPELINE HANDOFF — REVIEW:`. Put `RESULT` or `REVIEW` fields on the next line when required by `thoughts/shared/manager/worker-contract.md`. Return the outcome, evidence paths, checks, commit, and blocker if any. Claim a named test passed only from completed execution evidence (its `SCOPED_END`/`PASS` log line, typed per-test receipt data or exact test output); a `changed_modules` entry, filter, selected count, compile success or `gate_covers_rest` is plan intent, not a run. Report the executed count and label touched tests the bounded plan omitted `UNRUN` or `source-inspected`, naming who covers the residual (#250; detail in `thoughts/shared/manager/worker-contract.md` section 4). Prefer file and line references over excerpts; leave code and detailed artifacts on disk. If incomplete, report a precise partial result and observed blocker evidence. Budget or review exhaustion calls for continuation, not a fabricated human gate. The handoff's last line is `Friction: none | #N[, #M] | <one line, not filed because ...>` (#1332); `rsi-contract-validate` accepts it and does not yet require it. The daemon's stranded check also accepts a near-miss header line (`**IMPLEMENTATION HANDOFF — ...**`: markdown emphasis, `<STAGE> HANDOFF` order, no colon) as a final report and annotates the terminal watch `handoff_header_normalized: <STAGE>` (#2525); `rsi-contract-validate` still requires the exact form. A Completed worker with no marker line in its final turn is labelled `no-result: stranded`; when it published a handoff to its bound Issue the watch says `no-marker: issue handoff published, read it (not a verified result)` instead (#187), so a hold, a partial and a finished result are told apart by reading the record, never from the label.

**Already satisfied (#2651).** An Issue-pipeline implement worker whose Issue's acceptance already holds on its base (a stale red, a duplicate, a sibling landing) makes no commit and hands off `status: already_satisfied` with `evidence_commit: <lowercase 40-hex commit>` and its verification lines (tests run, results), with a clean worktree, instead of `status: complete`. The executor accepts it only when the commit is an ancestor of the attempt's base, the worktree is clean and the attempt added no commit; it then settles the node `succeeded` without a result commit, treats land, review and follow-up as dead paths, settles the execution `succeeded` and closes the Issue with a note naming the evidence commit and the verification lines. A missing, malformed or non-ancestor `evidence_commit` fails the node `handoff_invalid`. The evidence commit must also be an ancestor of a freshly fetched `origin/rolling` (#3045): when it is only reachable from a supplied `base_commit` that is not on rolling, the work is not landed, so the executor treats the handoff as the #2732 `complete` handoff at that base (land runs, the Issue is not closed here); when that route does not apply (a repair, retry or non-first node) it fails `handoff_invalid`. `evidence_commit` is valid on no other status.

**Verify supplied work (#2732).** Satellite or operator work that needs hub verification is run through the starter: start `issue-pipeline-post-review` with `base_commit` set to the supplied commit. When that commit is not an ancestor of a freshly fetched `origin/rolling` (git positively says so; a fetch outage counts as "cannot say" and keeps the rule below), the first implement node (whose base is the execution's `base_commit`) verifies the head unchanged and hands off `status: complete` with `commit` equal to that base and its own passing `scoped_test` at it, making no new commit. The executor accepts that as the node result (`result_commit` = the base, `changed: false`), then land and review run as for any commit. Not `already_satisfied`: that closes the Issue without landing. With the base already on `origin/rolling`, or for a repair or later node, the rule stays: `complete` without a new commit fails `handoff_invalid: node handoff requires a new commit`.

If a `## Stage contract` appears, `rsi-contract-validate` checks `### Inputs`, `### Process`, `### Outputs`, `### Verify` in order. Inputs must name a static artifact or explicit `rg`/glob discovery budget. The block is optional for historical handoffs; an incomplete block fails validation. The including command may require it.

Write a handoff document after other edits and commits. If more files change afterward, refresh its recorded `git_commit:` before return. Commit task-owned `thoughts/` artifacts. Use the worktree-isolated `scripts/rsi-stash` interface for stash operations. For issue control authority and payloads, read `.agents/skills/rsi-agent-control/SKILL.md` on demand. For disk pressure during builds, check `df -h /tmp .` before diagnosing SQLite write errors as product defects. A scratch write refused with `Disk quota exceeded` (EDQUOT) while `df` shows free space is a per-user quota on the mount (#565): `rsi-rpc scratch-quota [PATH]` prints the mount's quota options and your usage. Pass a control payload with `rsi-rpc <Verb> --params -` (stdin) instead of a `/tmp` file, and capture evidence through a pipeline only under `set -o pipefail`, so a failing producer or a refused write cannot record a red gate as a pass.

Reconcile a plan's conflicting requirements before implementation. Assert positive user-visible identity in tests. The canonical form of these repository rules is `AGENTS.md`.
