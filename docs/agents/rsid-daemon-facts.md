# rsid daemon facts

Full text of the entries that used to sit in `crates/rsid/AGENTS.md` ("Facts that bite").
That file keeps one line per fact and points here by section; this file holds the
mechanics, identifiers and history. Read the section for an area before you change
it. RPC family contracts stay in `docs/agents/rsid-rpc-contracts.md`.

A crate `AGENTS.md` has a size ceiling (`scripts/repo-guard agents-md-size`, 12 KB): add detail
here, and add at most one line to the crate file.

## Agent mail and hooks

### Agent mail delivery

Agent mail: `queued` is not delivered. The default expiry is 30 minutes from
first acceptance (6 hours when the recipient owns an armed result wake or
open job, including before its turn ends, #2411; a parked session accepts
mail and gets it at its next resume, #2144; a session with a final
handoff or nothing to resume it still refuses `target_terminal`). Claude sessions also get it at each tool boundary through the per-session PostToolUse hook (`rsi-rpc boundary-mail-hook` -> hook-only `ClaimBoundaryMail`, `session/boundary_mail.rs`, #1049); Codex CLI launches (Codex, Pioneer, Codex-routed OpenRouter/Bedrock) install the same hook with `--mail-only` as a `-c hooks.PostToolUse` override and trust exactly that hook with a `-c hooks.state` key+hash override (never `--dangerously-bypass-hook-trust`; `codex.rs`, #1183); the hook runs only the daemon's installed absolute `rsi-rpc` sibling, never one from `PATH` (no sibling, no hook); hook-claimed agent mail stays `claimed` until the hook calls `ConfirmBoundaryMail` after printing AND the provider transcript named in that call shows the hook context accepted (Codex `hooks.additional_context` item, Claude `hook_additional_context` attachment); anything else settles `uncertain` at `BOUNDARY_MAIL_CONFIRM_DEADLINE`; every Harness-loop session (Harness, Harness-routed OpenRouter/Bedrock) takes it between model calls (`harness/agent_mail.rs`). Local, Antigravity and CodexAppServer get mail only at turn end, and `AgentSendMessage` says so (`delivery_boundary: "turn_end_only"`). The same hook also spills large tool results (PostToolUse `updatedToolOutput` for Bash/Grep) and routes heavy Bash commands (cargo, make, test runners) through `rsi-rpc spill` at PreToolUse (#1097, `rsi-common/src/spill.rs`; a failing command is a `PostToolUseFailure`, which cannot rewrite output, hence the PreToolUse route).

### Headless AskUserQuestion

Headless `AskUserQuestion` (hub #13, hub #1161): every rsid-launched Claude run is headless `-p` stream-json with no permission-prompt tool, so no human can answer the question. The per-session `--settings` (`boundary_mail_hook::claude_settings_json`) carries a second `PreToolUse` group, matcher `AskUserQuestion`, running the same `rsi-rpc boundary-mail-hook` command; the hook denies it with `permissionDecisionReason` = the typed `[rsi:ask_user_question_undeliverable]` notice (`rsi_common::ask_user_question_notice`, the one text `session/question.rs` re-exports), which the CLI hands the model as that call's tool result in the same turn. It makes no daemon call; a hook that fails or times out leaves the CLI's own rejection, and the next-continuation notice (`with_unanswered_notice`) stays the fallback. Delivering the operator's live answer in-turn is not implemented (needs a blocking answer channel such as an MCP tool).

Claude per-turn token overhead (#3565): every Claude launch sets `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=off` (`claude.rs`; the CLI's own override of its `<total_tokens>N tokens left` reminder, which cost 36-47k tokens per manager seat; rsid measures context fill itself, so the cap rotation is unaffected). The `rsi-agent-mcp` gateway asks the daemon once, on its first `tools/list`, for the caller's catalog roles (5 s budget, any failure = worker) and, for a `manager` or `global_manager` seat, marks `MANAGER_PRELOADED_NATIVE_TOOLS` (`rsi-common/src/agent_control_schema.rs`) with `_meta["anthropic/alwaysLoad"] = true`, so Claude Code puts those schemas in the prompt instead of re-loading them through `ToolSearch` (17-20k tokens per seat). Every other tool stays deferred and a worker preloads none. A new hot tool is added to that list, which a test checks against the native tool names.

## Deploys and shutdown

### Upgrade-boundary members (#587)

Staging walks the staging daemon's compiled `DEPLOY_BINARIES`, so a commit that
adds a member cannot carry it on its first upgrade. After the new build
verifies, `DeployService::complete_upgrade_members` installs each plain binary
the manifest skipped from the `bin-<sha>` stage under the staging root
(same copy, mode and sha-256 checks; never `rsid`, the supervisor or the tool
scripts). The settled reason names what it installed, or `PARTIAL INSTALL` with
the members left out; the fix for the latter is a re-deploy or
`make release-install NOW=1`.

### Deploy quiet point and interrupt_workers

`AgentRequestDeploy` waits for a quiet point (no landing, local job or
worker mid-turn). Peer deploys default `interrupt_workers` to true; local
hub deploys default false, and explicit false waits for a lull on either.
`interrupt_workers: true` (#1461) makes a worker mid-turn
stop blocking once the `deploy_drain_hold_secs` hold is over, records and
names the interrupted workers (V158 columns, `deploy_interrupt` friction) and
resumes them through the restart journal (a topology node session is named with its execution and node in the outcome; if the journal cannot resume it, the executor preserves its diverged work and retries the node once from the preserved commit as an infrastructure loss, #2549; that retry may hand off the preserved commit unchanged once it is verified, #2568; a journal hold `operator_paused`/`pending_question`/`review_owned` on a clean sandbox keeps the attempt held with no replacement, #2569); a landing or a local `build` job
still blocks. A manager's ordinary child `on_terminal` watch is not spent by that interruption while the restart journal still owns the turn (`worker_terminal_watch_pending`, `Interrupted` + `restart_intent_will_continue_session`, hub #2987): it fires on the continuation's real end, or at once if the intent failed or waits on a hold (`operator_paused`, `pending_question`, `custody_changed`, `competing_owner`), which the watch reports as the stop reason. The operator DRAIN wait then stops waiting for exactly the
workers the restarting deploy named (`DrainState::DeployInterrupted`, read
from the deploy row in the same classification, #2371); managers, other
sessions and every deploy without `interrupt_workers` keep the full wait. Running `test`/`scoped_test` jobs are never stopped or
requeued by a deploy (#3554): their units are `systemd-run --user` services outside rsid's process tree and their wrapper writes the
status file itself, so they run across the restart, and the new daemon's startup poll finds each `running` row, sees the unit active
(re-adopted) and settles it once with its one owner wake. They do not block the quiet point (`deploy_surviving_jobs`); the restarting
poll marks the jobs still running as `survived_deploy` in their params (no schema change) and the receipt and outcome wake name them
(`surviving_jobs`; `expected_surviving_jobs` while staged). A running landing, build or protected test still blocks the quiet point, and
a hub QA run settles `interrupted_by_deploy` instead (`stop_hub_qa_for_deploy`). An older daemon requeued tests after
`DEPLOY_JOB_GRACE_SECS` (#2278, #2204); `requeued_jobs`, `expected_requeued_jobs` and `job_grace_secs` stay as legacy receipt fields.
A survivor's cargo-slot lease is not known to the new daemon's in-memory governor, as after any unplanned restart. New `test`/`build` jobs are held
(`held_for_deploy`; a staged deploy without `interrupt_workers` holds them to its deadline too, no retry window, #3373) and the merge queue admits no new batch for the whole staged
deploy (#2190); a timed-out `interrupt_workers` deploy keeps new jobs held 300 s
past its deadline (continuous with the staged hold, owned by its deploy id, restored
after a restart) so its retry is not raced (#2278, #2551-#2553). Contract: `docs/agents/rsid-rpc-contracts.md` ("Deploys").

### Shutdown backstop

Shutdown backstop (#2561): `scripts/rsid-supervisor.sh` ends a daemon shutdown that outlasts the operator setting `supervisor_shutdown_grace_secs` (60-3600 s, default 120, TUI Settings > Merge queue; line 2 of the `deploy-restart-budget` snapshot the supervisor reads). The daemon reads `RSID_SHUTDOWN_MARKER` once at the top of `main` and removes it from its environment (no child inherits it, #2594) together with every `RSID_SUPERVISOR_*` variable the script exports for itself (`RSID_SUPERVISOR_PATH`, `_SNAPSHOT`, ...; one list, `SUPERVISOR_INTERNAL_ENV`, #2601; `RSI_LISTEN_FD` is consumed at listener adoption), then marks a shutdown's start by writing `pid=<pid> reason=<code>` there (`supervisor_shutdown::mark_shutdown_begun`); the supervisor ignores and removes a marker naming another pid, and `rsid.service` `TimeoutStopSec=3700` covers the grace (#2590); past the grace the supervisor sends SIGTERM, then SIGKILL, to the daemon's process group, appends `~/.rsi/forced-shutdown-incident` and takes the exit-75 path. The next start records a `forced_shutdown:<trigger>` friction event and a manager notice from it (`surface_incidents`, after readiness). Unannounced signal stops (#3433): the daemon records who sent each SIGINT/SIGTERM (`signal_sender.rs`: an `SA_SIGINFO` handler chained after tokio's, sender pid/uid/`comm`/cgroup on the `daemon.log` line `Shutdown signal received: ...`, `sender_pid=` in the marker, friction `forced_shutdown:signal:<sigint|sigterm>`). The supervisor restarts a daemon that exits 0 after a marker with `reason=ctrl_c|sigterm` unless the stop was announced: it signalled the supervisor itself, or `pid=<daemon pid>` is in `~/.rsi/intended-stop` (`rsid_announce_intended_stop`, written by `install-release.sh` before its direct `kill -INT`; a new direct stopper must do the same). The restart goes through the exit-75 path and budget, appends `trigger=unannounced_signal` (or `restart_budget_exhausted` when the budget is spent and it stops) to the incident file, and a 2 s settle window lets a `systemctl stop` reach the supervisor first. A running TUI whose socket stays unreachable past 10 s starts the daemon through the startup auto-start (`app/daemon_recovery.rs`, at most 3 launches 30 s apart) or shows a persistent banner naming the start command. Unix only. Contract: `docs/agents/rsid-rpc-contracts.md` ("Deploys").

## Topology executor

### Settled-execution digest

Settled-execution digest (#2559): a settled (`succeeded`/`failed`/`cancelled`/`blocked`) execution carries `execution.outcome` on `AgentTopologyGetExecution`, and its `topology_execution_settled` wake appends the same digest (<= 1.5 KB, `topology/outcome.rs`): the input Issue and its status, per land node the landed SHA, queue entry, queue wall seconds and a refused Issue close's code (`issue_close=refused:<code>`, #2578: the queue published but the Issue stayed open), per review node the verdict, attempt number and reviewer model, the Issues the run's node sessions filed, and one line per failed or blocked node (attempt ids only there).

### Quiet clean success

Quiet clean success (#3387): the daemon's default `AgentTopologyExecute` settle wake carries a daemon-owned `$.quiet_settle` record (`Store::mark_quiet_settle`; a wake the owner armed itself never has it). When it observes a `succeeded` execution whose outcome is clean (`outcome::is_clean_success`: input Issue `Closed`, no failed node, no refused land close, every review `approved`, no follow-up filed) it opens no owner turn: `wake_when::quiet_hold` records the digest line on the row and moves its next check out by `QUIET_SETTLE_MAX_HOLD_SECS` (30 min). Any later predicate wake delivered to that owner appends the held lines (`quiet_digest`, read-only; the rows are retired only after the owner took the turn), and a line that waits the full hold is delivered alone as one batch. Every other outcome (failed, cancelled, blocked, an open Issue, a refused close, `changes_requested`, a follow-up, no input Issue) wakes at once as before. The hold is a constant, not an operator setting.

### Review evidence

Topology review evidence (#2570): every topology review query carries the test-evidence rules (the verified receipts are the evidence; no `scripts/scoped-test`; at most one exact-name test job to prove a finding), and a post-land query adds the merge-queue gate receipt for the published entry (`NodeEffects::land_gate_receipt`: filters, state, gate log glob). A reviewer that cannot run a check files a finding keyed `infra_*` (the legacy keys `focused_tests_unavailable`, `required_tests_unrun`, `tests_unavailable`, `tests_unrun` count too); a non-accepting receipt whose blocking findings are all such keys reads back `Unsettled(manager_review_infrastructure_unavailable)` (`rsi_common::harness_manager_v2::review_receipt_is_infrastructure_only`). The executor settles it `failed(review_infrastructure)`: an infrastructure class (uncharged against the attempt cap, retried with a fresh review after the capacity backoff, at most `REVIEW_INFRASTRUCTURE_RETRIES` times, then `blocked(review_unsettled)`), and the review ledger does not count that receipt as a spent round.

### Reviewer read

Topology reviewer read (#2982): the active reviewer of a review assignment that serves a topology attempt (`request_json.$.topology_attempt_id` -> `topology_node_attempts.execution_id`, `Store::topology_review_assignment_on`) may call `AgentTopologyGetExecution` for that one execution: `get_execution` skips the manager/lead scope check for it, and the catalog lists the verb through `VerbRights.topology_reviewer`. Every other topology verb, and any other execution, stays `authority_denied`; the read ends when the assignment leaves `active`. The reviewer's response also carries `receipts` (#3020, `topology/review_receipts.rs`): per session attempt the daemon-verified `scoped_test` receipt from its `verification` output (job, exact `head`, exit code, plan, failing/known/new failures, or the `unverified_reason`) and per published land attempt the merge-queue gate receipt (`land::gate_receipt`: entry, commit, state, filters, log glob), each list bounded; any other caller gets `receipts: null`.

### Review interrupted by a deploy

Topology review interrupted by a deploy (#2809): a `blocked` receipt from a reviewer session an `interrupt_workers` deploy recorded in `agent_deploys.interrupted_sessions` is no verdict on the code. `topology_review_outcome` reads it back `Unsettled(manager_review_reviewer_interrupted_by_deploy)` (`REVIEW_INTERRUPTED_REASON`), the executor settles it `failed(review_infrastructure)` (same uncharged budget and automatic relaunch as `infra_*`, no capacity backoff, the reason recorded in the attempt error), and `review_has_substantive_receipt` does not count it as a spent round, so the retry is not refused `review_round_unavailable`.

### Handoff format

Topology handoff format (#2584): a finished node whose last message the handoff parser refuses (`handoff_invalid`, e.g. prose before the marker line) is continued once as the same session with the parse error and the required first line (`node_handoff_format_continued`, counted apart from the other continuations); only a second malformed handoff fails the node. A node failure that ends the execution appends the SHA each land node published and each review verdict to the execution error (`outcome::failure_context`), so a failed post-review followup never reads as a bare `failed`. The `issue-pipeline-post-review` followup prompt shows the exact first line for both outcomes (filed, nothing new).

### Structured handoff

Topology structured handoff (#2759, `structured_handoff.rs`, `rsi_common::structured_handoff`): a session node with `structured_handoff: true` (or any session node while the setting `structured_handoff_default` is on, default off, TUI Settings > Provider Isolation) has the harness validate the shape of the handoff on the turn the executor opens to obtain it, the #2584 format continuation. `continue_handoff_format` arms the session (`structured_handoff::arm`); the provider spawn chokepoint (`spawn_provider_process`) consumes the arm once and sets `LaunchConfig.structured_handoff`, so Claude gets `--json-schema=<schema>` and Codex `--output-schema <file> -o <file>` (files in the session's execution scratch temp, removed when the message is read, `disarm`ed or re-armed); every other turn, provider and node is unchanged, and the daemon cannot know an ordinary turn is the last, which is why only the daemon-opened turn carries the schema. Claude's `result.structured_output` becomes the turn's assistant message rendered as the canonical `PIPELINE HANDOFF` block (`convert_recognized_stream_event`); Codex's last message is the JSON text, which `parse_pipeline_handoff[_v2]` and `observe_completed` normalise to the same block (`normalize_structured_handoff`); free text parses as before. The schema is strict-mode shaped (all fields required, nullable, no extras). Counters `handoff_observed_total` and `handoff_invalid_total` by `provider` and `structured` (the turn that wrote the message carried the schema) are on `AgentGetDaemonInfo` `handoff_counters`, in memory since daemon start. A new handoff field goes into `FIELDS` in `rsi-common/src/structured_handoff.rs`.

### Review Work rows

Topology review Work rows (#2607): the `topology:<execution>:<node>` Work rows a review node opens on the project manager's ledger belong to the execution, not to a lead. `Executor::settle_review_work` (`topology/review_work.rs`) records integration (the ledger `Integration` record at the published tip, only for a row whose source has an admitted acceptance and is an ancestor of a fresh `origin/rolling`, `landed_source_tip`) when a land node publishes and again in `settlement_cleanup` (`review_work_settled` event) when the execution ends, where every row that did not land is retired (archived). The same pass backfills executions that settled earlier. Operating-intent reconciliation never counts a `topology:` row as unfinished work, so such an Epic needs no lead and recovery never relaunches one for them.

### Supplied-base handoff

Topology supplied-base handoff (#2732): an execution whose `base_commit` is not an ancestor of a freshly fetched `origin/rolling` (`NodeEffects::commit_off_rolling`, false when git cannot say) lets its first implement node hand off `complete` with no new commit; the node settles on its own receipt at that head and land/review run. Contract: `docs/agents/worker-contract.md`.

### Already-satisfied handoff

Topology already-satisfied handoff (#2651): an Issue-pipeline implement node (`expects_commit` in a workflow with a `close_issue` land) whose worker proved the acceptance already holds on its base hands off `status: already_satisfied` with `evidence_commit` (lowercase 40-hex) and no commit. `observe_completed` accepts it only when the commit is an ancestor of the attempt base, the tree is clean and the attempt added no commit (`accept_already_satisfied`), otherwise `handoff_invalid`; the evidence must also be on a fresh `origin/rolling` (`commit_off_rolling` false, #3045): evidence only in a supplied off-rolling `base_commit` is handled as the #2732 `complete` handoff at the base (land runs), or `handoff_invalid` when that route does not apply. The node settles `succeeded` with `fields.already_satisfied` and no result commit, so its `success`/`completed` edges are untaken (`edge_taken`) and land, review, repair and follow-up are dead paths; the execution settles `succeeded` and the input Issue is closed as the execution owner under key `topology-satisfied:<execution>:<attempt>` with a note naming the evidence commit and the worker's verification lines (a refused close is `fields.issue_close`, the Issue stays open). #3772/#3808: the handoff must carry a `summary` with one `AC<n>: <evidence>` line per Issue acceptance criterion (`issue_close::issue_acceptance_criteria_count`) and `tests` entries of the form `<command>: <result>` (`satisfied_proof_gap`; else `handoff_invalid`, `already_satisfied_unproven`), and an `operator-request` Issue is never closed on the claim (`issue_close: held`, `manager_acknowledgement_required`; the Issue stays open for the manager). Contract: `docs/agents/worker-contract.md`.

### Dirty finish

Topology dirty finish (#2563): an implement/repair node (`expects_commit`) that hands off `complete` but leaves uncommitted paths is continued once as the same session (`node_uncommitted_continued`, counted apart from the verification continuations) to commit or discard them; a second dirty end blocks as `preserved_work`. A parked node is running, not terminal (#2625): an `Interrupted`/`Failed` session (its process died between turns) that owns an armed result wake, a live owned `owner`-wake job or a job that settled since its last turn stays `running` whatever its sandbox holds (`parked_awaiting_resume`, shared with the `Completed` between-turns rule); only a session nothing will resume has its dirty tree preserved. `ResolveTopologyAttempt accept` on a `preserved_work` attempt makes its verified preserved commit the node result; the clean-tree rule applies only when no preserved commit exists. On a `require_verified` node (#2621) the accept binds the session's own `scoped_test` receipt for exactly that commit as the node's `verification` (so land admits it); with none it is refused `topology_preserved_unverified`, whose next step names `retry` or a verification job.

### Land retry

Topology land retry (#2548): a land attempt blocked `land_admission_lost` (the requester's seat rotated, the acceptance stopped admitting) holds no work, so `ResolveTopologyAttempt`/`AgentTopologyResolveAttempt` `retry` (not `accept` or `discard`) records a new land attempt on the same commit (`land_retried`); its enqueue re-checks land authority live, so the execution continues to its land and `post_review` nodes once the cause is cleared and a still-unauthorized retry blocks again with the same evidence.

### Node questions

Topology node questions (#1641 S3b/S3c): a node's pending question, a BLOCKED
handoff with `blocker_question`, and a review that ran out of rounds all park
the attempt for the on-call manager. A BLOCKED handoff or an exhausted review
files a `topology:` decision on the PM ledger (`topology/decision.rs`;
`gate` follows `blocker_class`, so gate classes reach the operator); the
ruling continues the same session. The executor registers a node waiting on
an answer (`oncall::note_answer_wait`) and `stall_detector::stall_threshold`
exempts it from every stall action; the execution deadline still applies (a parked
decision is withdrawn and the attempt times out at it). The ruling's answer reaches the
session through `NodeEffects::continue_with_answer` (`ContinuationIntent::TopologyAnswer`):
the exact execution/attempt/decision binding is rechecked under the spawn guard and
durably claimed (`delivery.state = started` in the attempt marker) before the provider
effect; a claim with no sign the session took the answer is shown uncertain, never
resent (#1715).

### Context-cap baton

Topology context-cap baton (#3340, `topology/baton.rs`): a session node that crosses the worker context cap (#1254) is told (`worker_baton::baton_steps`, record field `topology_node`) to end with `PIPELINE HANDOFF — BATON <sha>`; the executor reads that first line as the node's outcome before the strict handoff parser, so the session is not re-prompted (`observe_completed` -> `settle_context_cap_baton`). The sandbox commit (uncommitted paths snapshotted, as `preserve`) is preserved, the attempt settles `interrupted` / `context_cap_continued` (uncharged, in `failure::INFRASTRUCTURE`, own budget `MAX_CONTEXT_CAP_CONTINUATIONS` = 3 per node instance in `retry_due`, apart from the `LOSSES` budget), and `schedule` relaunches the node from `preserved_commit` with the baton appended to its query (`retry_query`, `Context-cap continuation (n of 3)`, a later baton replaces the earlier one). A baton past the budget blocks `preserved_work` for `ResolveTopologyAttempt`; a baton is not a #2563/#2549 retry (`restart_retry_spent` ignores it). The launcher's `worker_context_cap` mail says the execution continues the node, not `continue_from`.

### Topology Issue handoff records

Topology Issue handoff records (#3757, `topology/starters.rs`): the `inputs.issue` snapshot taken at accept also copies the Issue's newest `ISSUE_HANDOFFS_MAX` (5) append-only `issue_handoffs` records (each clipped to `ISSUE_HANDOFF_MAX_BYTES`, labelled with the author's `sessions.agent_role`, `session` when none) and `handoff_total`; `render_issue` quotes them after the body so a worker sees manager rulings and reopen evidence written with `AgentUpdateIssue {handoff}`. An Issue with no records keeps the old snapshot shape. Records written after accept do not reach a running execution, like the body.

### Issue auto-dispatch

Issue auto-dispatch (#3390, `topology/auto_dispatch.rs`): an `Open`, ready (`list_ready_issues`: no open blocker) Issue labelled `dispatch:auto` is launched by the daemon with no manager turn. `SessionManager::dispatch_auto_issues` runs on the 15 s housekeeping tick in `main` (one cheap query when no Issue carries the label) and calls `agent_topology_execute` as the project's current manager seat, so the seat owns, sees and can interrupt the execution, its settle wake still arrives, and policy, pause, `max_created_sessions` and digest admission apply unchanged. Eligibility is the pure `classify`: not archived, not `satellite:*`-assigned, no migration/credential/IAM/network-exposure label (those stay with the PM, who picks `issue-pipeline-reviewed`); `authority`/`custody`/`lander`/`queue`/`deploy` labels route to `issue-pipeline-post-review`, everything else to `issue-pipeline`. A pass is skipped while host-load or pressure admission holds; per project at most `min(max_active_sessions, 5)` executions holding a session node (reserved, launching or running; `session_holding_executions`, plus one just accepted with no attempt yet) are counted (the 5-build-heavy-session rule), and total open executions stay under `OPEN_EXECUTIONS_CAP` (30), so executions parked at land, review or a decision never starve new dispatches (hub #3699); three start per tick. An Issue that any execution ever held (live or settled, any requester) is never auto-dispatched again, so a failed run goes back to the PM instead of a retry loop; an admission refusal backs the Issue off for ten minutes in memory. The kill switch is the existing `topology_executor_enabled`. The settle wake still resumes the seat for every settle (the quiet-success follow-up is #3387 part 2).

### Manager action error detail

Manager action error detail (#3640): `safe_action_error` still maps every error to a static class, but an action that ends in the catch-all `manager_v2_lifecycle_unconfirmed` also keeps the original error text on its receipt as `outcome_detail` (`manager_actions::bounded_error_detail`: secrets redacted, control characters flattened, 300 chars) and records one `manager_launch:<action_kind>:manager_v2_lifecycle_unconfirmed` friction event (codes and the action id only). A fresh-launch `ContextRead` custody refusal (`session_context_authorization_failed`) keeps the same bounded detail on the failed session's explanation event. A topology review whose reviewer launch ended that way (or settled with no reviewer session) reads `Unsettled("<code>: <detail>")` and settles `review_launch_refused`, which shares `review_unsettled`'s one-retry-then-block budget and resolve rules.

## Host load and job resources

### Host-load admission

Host-load admission (#1417, `host_load.rs`): a manager's queued
new `create_session` stays unclaimed (`claim_manager_action_with_create_admission`) and
a topology node stays `Reserved` (`NodeEffects::launch_held`; every
execution's later nodes, only the first launches of an operator execution
are immediate, #1641 S4b) while `load + recent_admissions >
host_load_admission_threshold`; only those two paths, the merge queue's
async full-library QA start (`rolling_queue/bounded_qa.rs`, which only
waits, #2112, and stops waiting on host load once a pending landing is 3 hours
old, logging a typed `bounded_qa_held` reason per change, #2394; a deploy drain
is never bypassed) and a satellite accepting a hub QA run (`RequestHubQaRun`,
refused `satellite_qa_busy`, #2120) consult the gate; Issue worker continuations, topology retries
and launches already in progress bypass it. Capacity pressure never fails a node: a `-32029` sandbox refusal
or an ungranted governor build slot (command nodes) leaves it `Reserved` with
one `admission_hold{kind}` event per transition. Eligible creates and topology waiters
share the held order. In unit tests (`cfg(test)`, `test-seam`) the load
source defaults to unsupported, so a loaded CI host never holds a test; a
test of the hold installs one with `host_load().set_source(..)`. Contract:
`docs/agents/rsid-rpc-contracts.md` ("Host-load admission").

### Build source custody

Build source custody (hub #2954, `agent_jobs/source.rs`): a `build` job compiles one commit. Submit records the job worktree's HEAD and dirtiness (`observe_clean_head_bounded`, sidecar `<jobs>/<id>.source`, no migration) and optional `params.sha` pins it (`job_source_sha_mismatch` at submit; an unwritable record refuses the build `job_source_record_failed` before the row exists, #3025); the queued start, every jobs-loop poll while the unit runs (slot wait and grant included) and the finish compare, and a moved HEAD or a clean tree that became dirty fails the job `job_source_moved` naming both SHAs (a dirty-at-submit tree only fails on a HEAD move). `result.source_head`/`source_dirty` are the deploy-comparable receipt. Contract: `docs/agents/rsid-rpc-contracts.md`.

### Job TMPDIR Git ceiling

Job TMPDIR Git ceiling (#2612): a build/test/landing/cloud-gate unit with a private `TMPDIR` (`<jobs>/<id>.tmp`) also gets `GIT_CEILING_DIRECTORIES=<that TMPDIR>` (systemd `--setenv`, launchd plist; `GIT_CEILING_DIRECTORIES_ENV` in `agent_jobs.rs`). The jobs directory is under the operator's home directory, which is itself a repository, so without it plain Git in a test's temporary directory discovers the home repository and `scripts/scratch_git.py` (which finds the working tree around its cwd the way Git does, ceiling included) refuses every fixture as "inside protected root" (the full-library QA red of #2612). Git does not look at the ceiling or above it, and only for a cwd below it, so the job's source checkout and any repository made inside the TMPDIR are found as before.

### Job CPU custody

Job CPU custody (#2524): every cargo unit a job starts is bounded by
`min(job ceiling, rsi-build.slice budget)`. The daemon stamps the outer unit
from `build_slice::current_job_ceiling_percent`; `scripts/scoped-test` reads the
slice's live `CPUQuota` (`slice_budget_percent`) and lowers its `--cpu-quota`
to it, and every nested `rsi-scoped-test-*` unit carries `--slice` and that
`CPUQuota`. A satellite is the same `rsid`: `main` applies
`hub_build_cpu_percent` to its slice at start (`build_budget::apply_at_start`),
so the laptop's budget is its own operator setting. A caller may lower one job's budget with `cpu_quota_percent` (100-1600, package/shard/`scoped_test`/build params, #161): `agent_jobs::apply_requested_cpu_budget` takes the smaller of it and the derived quota for the outer unit's `CPUQuota`, the scoped-test `--cpu-quota` (so nested units and nextest threads follow) and, for plain cargo jobs, `RSI_JOB_BUILD_JOBS`/`RUST_TEST_THREADS`/`NEXTEST_TEST_THREADS` (at most `cargo-slot`'s default four); it never raises a budget and is refused for a recipe. Thermal guard: the operator
setting `job_thermal_ceiling_c` (default 85 C, 0 off, TUI Settings > Merge
queue; `rsid_core::thermal_guard`, Linux hwmon CPU sensors, nothing holds
elsewhere) holds a new build/test/landing/cloud-gate job `held_for_thermal`
(queued, no unit, no timeout clock) while the host is at or above it.
The predicate is shared (#2562, `host_pressure`): the same thermal gate and the
governor's `min_free_disk_gb` floor also hold a manager's new `create_session`
and a topology node's first launch (`held {reason: thermal|disk_pressure}`,
`admission_hold{kind}`), through the host-load queue, oldest first.

### macOS resource governance

macOS resource governance (#2937, `host_memory.rs`): the 16 GB, 12-core Mac Mini satellite runs cargo units directly (the slot wrapper is `/usr/bin/env`, `cargo-slot` needs Linux tools), so the daemon bounds them itself. `read_host_load` and the satellite `load_avg_1m_milli` use `getloadavg(3)` off Linux (`daemon_info::load_average`); the governor's memory sample reads `vm_stat` free + inactive + speculative pages (no purgeable double count). `GovernorPolicy::platform_default()` is the Linux hub policy (`LINUX_DEFAULT`: 4 build, 5 lander, 2 check slots, 16 GiB available) or, on macOS, `MACOS_16GB_DEFAULT` (2 build, 1 lander, 1 check slot, 4 GiB available; `config.rs` seeds the `governor_*` settings from it, so the operator still tunes them). `agent_jobs` holds a new cargo job `held_for_capacity` (queued, no unit, admission clock running) while running cargo jobs >= `build_slots` or available memory < `min_avail_mem_gb`; the gate is on only when `host_memory::CAPACITY_GATE_ENABLED` (macOS) and reads the live `governor_build_slots` / `governor_min_avail_mem_gb` through `GovernorPolicy::live_job_gate()` (a process-global the store publishes on every write and at startup apply, like `thermal_guard::set_ceiling_c`, #2951). The CPU andon samples launchd job services on macOS (`launchctl list` pid + `rsi-job-<id>` label, then `proc_pid_rusage` self plus reaped-children CPU of the root process, `cpu_andon::sample_trees`, #2951); provider scopes have no launchd service there and are not sampled.

## Satellite QA and QA target

Manager QA worktree target (hub #3870 b): a job whose cwd is a direct `qa-*`
child of `~/.rsi/deploy` and outside every sandbox builds in the owner seat's
one warm target (`agent_scratch_reclaim::seat_qa_target`, name
`rsi-build-qa-seat-<hash of the seat sandbox root>`), not a fresh per-worktree
one. The seat root is its registered source, so the 72 h age floor holds it
while the seat lives and a gone seat orphans it (#646). One build at a time per
target is the job admission lock; `qa_target_max_gib` empties it before a build
when over the cap. A successor seat starts cold and the old target is reclaimed.

### Satellite full-library QA

Satellite full-library QA (#2120): the merge queue's async full run
(`rolling_queue/bounded_qa.rs`) is placed on the first enabled, paired,
dispatch-enabled, scoped peer whose poller observation is healthy and under
15 minutes old and whose live identity advertises `qa_run` and a
`qa_admission` that admits (`satellite/qa_link.rs`). The satellite computes
that admission (health) and rechecks it at start from the same gates its
job meets: its build governor's `min_free_disk_gb` (never below
`SATELLITE_QA_MIN_DISK_FREE_BYTES`) and other governor gates, host-load
admission and no other full-library job (#179). It
(`RequestHubQaRun`, operator-only, `rolling_queue/satellite_qa.rs`)
owns it as an ordinary recipe job under its live scope seat in
`<jobs>/rolling-library-qa/hub-<run>/source`, so it reuses the one
registered target. The hub binds the landings to a run id derived from the
anchor landing and its prior capacity deferrals (a retry or restart replays it;
a run that ended `job_admission_timed_out`/`job_start_timed_out` is deferred, not
filed, and its landings get a new run id, #2149), polls once a minute and
settles from the sanitized receipt; unreachable past 240 minutes is
incomplete coverage. A pre-send failure or a listed refusal
(`SATELLITE_QA_PASS_THROUGH`, raised before the satellite records a run) is a
non-effect and falls back (next peer, then the hub, `ran_on: hub` with the
reason); a lost or malformed start reply, or any other satellite error, is
uncertain (#180, #2156): the run stays bound to that peer and run id with
the satellite job unknown, no other peer or hub run starts, and each poll
replays the idempotent start (no fresh-placement admission) to reconcile it.
A launch error that left the satellite's job running answers with that job's
receipt, never a refusal. The peer, run id and commit are recorded
(`bounded_qa_dispatching`) before every start is sent and released
(`bounded_qa_dispatch_withdrawn`) only by a refusal that proves a
non-effect; an intent without a binding (the hub stopped after the
satellite accepted the start) is bound to that exact peer on the next pass
(#2155), so one obligation never runs twice. #2176: the run is a guest.
A deploy staged or restarting on a peer (its `health.last_deploy`, or its
admission `satellite_qa_deploy_pending`) keeps the run off it; when no other
satellite takes it the run waits for that deploy (re-asked once a minute)
instead of loading the hub. A staged deploy stops a running hub run at once
(`stop_hub_qa_for_deploy`, no grace), and the hub defers any
`interrupted_by_deploy` run as `deploy_preempted` (the #2149 path, no Issue).
Placement needs free disk of at least the governor floor plus the run's
target (`target_bytes`: last measured, else 25 GiB); after each settled run
the satellite's jobs loop empties the shared QA target and records its size
(`satellite_qa::reclaim_settled_runs`).

### QA target custody

QA target custody (#2509): the one reused QA target never grows past roughly one
commit. After each run, once no full-library QA job is queued or running, the jobs
loop calls `qa_target_trim::trim_settled_target`, which removes the artifacts a
newer run superseded while holding the target's admission lock (never racing a
job): a crate's older `deps/`, `.fingerprint/`, `build/` and `incremental/` entries
go when a newer entry of the same crate was written since the previous trim (the
`.rsi-qa-trim-stamp` mtime), while a dependency no run touched stays warm. The

Settings > Merge queue): `prepare_build_environment_in` empties a QA target above it
before the next run. The satellite empties its target outright after a settled hub
run (#2176) and the same cap applies to its own queue runs.

### Health wake

Health wake (#2747): a manager arms one `when.health_anomaly` wake instead of an hourly resume; the scheduler evaluates it every minute with no model call (`health_anomaly.rs`: pure `evaluate` over store facts, the host reading and `SessionLauncher::health_live_inputs`) and resumes the owner once, naming each `kind` and `subject`. Thresholds are the settings `health_disk_used_pct`, `health_thermal_c`, `health_stuck_minutes` (TUI Settings > Merge queue). The wake observes only the projects the owner's grant covers right now (`Scope::live`: stored `project`/`projects` intersected with the current grant, #2788), and an overrun attempt is judged against its real wall limit (execution deadline or node wall time, #2786). Contract and condition table: `docs/agents/rsid-rpc-contracts.md` ("Wake predicate `health_anomaly`"). A new condition needs a `KIND_*`, an `evaluate` arm and an injection test, and is listed in `every_kind_is_covered_by_an_injection_test_above`.

### Maintenance pass summaries

Maintenance pass summaries (hub #2940, `rsid_core::pass_cost`): each sandbox-custody maintenance lane logs ONE bounded line per pass, never one per candidate, carrying wall time, CPU, read volume and proof-outcome counts, so a burst of daemon CPU is attributed to a lane from the journal (`journalctl --user -u rsid`, not `~/.rsi/daemon.log`): `Archived sandbox purge pass finished` (per-stage `stage_cpu_wall_runs=name=cpu_ms/wall_ms/runs`, `fenced`, the dependency proof's `dependency_*` work counts), `Sandbox absent-root adoption pass finished`, `Session retention pass complete` (`store_lock_wait_ms`, `store_lock_held_max_ms`), `Sandbox build-cache reclaim pass completed` (`worker_thread_cpu_ms`) and `Automatic source settlement pass finished` (`audit_wall_ms`, `apply_wall_ms`). `thread_cpu_ms` and `*_cpu_ms` from a `ThreadMeter` are the pass's own thread time (Linux only; other platforms report 0 and keep the wall clock); `process_cpu_ms` of the settlement pass is a whole-daemon upper bound. `Store::source_worktree_targeted_dependencies[_for_absent_root]_with_work` returns the `DependencyProofWork` (relevant Sessions and enabled jobs freshly validated per proof: the cost is that scan repeated per candidate). The periodic purge loop (not the operator RPC or a dry run) skips a candidate whose identical row was retained inside a backoff window of 15, 30, then 60 minutes (`sandbox_purge_fence.rs`): a skip only ever re-uses a retaining verdict, a purge always runs the full proof chain, and any change to the candidate row re-proves it at once.

### Automatic settlement audit fence

Automatic settlement audit fence (hub #3031, `settlement_audit_fence.rs`): the 300 s automatic pass skips the audit of a cohort whose last audit succeeded with nothing to apply while its inputs are identical (store inventory rows with Session status/`updated_at`/dependency digests, latest run id, runtime holders that own or sit inside a root, and the observed settlement target tip read from the local ref with no fetch, hub #3056: a moved tip re-audits on the next tick, an unreadable one audits), for 10, 20 then 30 minutes (cap); `audit_fenced` is on the `Automatic source settlement pass finished` line. It skips only the audit: resume, the recovery-fence sighting, every apply and its holder proofs and the #2630 streak are unchanged, a failed audit is never remembered, an applyable audit forgets the entry, and relief from disk pressure clears the fence. External holders and a cleaned tree are not inputs, nor is a target advance the daemon has not fetched locally: the 30 min cap bounds them.

## Sandbox and harness custody

### Sandbox branch custody

Sandbox branch custody (#2320, hard rule 2): the same lexical git scan guards every provider family. `rsi_common::custody_scan` holds the scan (branch change, `reset --hard`, stash, force push, forced branch update, git aliases, discards of dirty paths); the Harness `shell`/`exec_command`/`git` tools settle it with an async probe (`harness/tools/custody_guard.rs`), and the CLI provider hook settles it with the blocking `check_command_sync` at PreToolUse (Claude `Bash` matcher in `--settings`; Codex a session-flag `hooks.PreToolUse` for `Bash`, trusted by key `:pre_tool_use:0:0` and a hash RSI computes, `codex.rs`; the provider contract canary checks that the installed codex-cli reports that same hash and `trusted`, #2755, and an untrusted custody hook refuses Codex launches while `codex_refuse_untrusted_custody_hook` is on). The scan also refuses a `cd`/`pushd` into a scratch or temporary location followed by an unpinned repository-changing git command in the same line, because a failed `cd` would run it in the sandbox (#2571; fixtures use `git -C <absolute dir>` or `scripts/scratch_git.py`, `docs/agents/worker-contract.md`). A `checkout`/`switch` whose `git -C` chain starts at a literal absolute directory (no `--git-dir`/`--work-tree`/`GIT_DIR`, no variable) is refused only when that worktree resolves to the session's own sandbox (same git dir, or a top level under the sandbox base) or cannot be resolved, so `git -C <manager deploy worktree> checkout --detach <sha>` passes (#2573; `branch_change_verdict`, the refusal names the resolved worktree; `--ignore-other-worktrees` stays refused). The hook checks only a command whose cwd is under `RSI_SANDBOX_BASE` (default `~/.rsi/sandboxes`) or that names a path under it (`rsi_common::boundary_mail_hook::command_in_custody_scope`); the Harness `shell`, `exec_command` and `git` tools use the same predicate (#3165: a scratch or benchmark-task repository elsewhere may `git stash` and `reset --hard`; a host with no resolvable base fails closed; a container target skips the scan and the kill guard, a host session keeps the kill guard). At each turn end `session/branch_custody.rs` compares the sandbox HEAD with `Session.sandbox_branch`: a clean worktree is switched back through the store's bounded Git runner (`restore_branch_bounded`: `--no-overwrite-ignore` so ignored and untracked files are never overwritten, `--no-recurse-submodules --no-guess`, a moved submodule pointer is refused, fsmonitor and hooks off, killed at 15 s; after a kill the daemon removes the `index.lock` Git left and puts the touched tracked paths back, and a refusal or timeout is a drift whose notice says the tree may be partially switched, #2539/#2541/#2556/#2557); a dirty one or one with an unfinished merge/rebase is left alone; both publish an operator-visible `SystemMessage` (warn for a restore, error for a drift).

### Harness container exec target

Harness container exec target (#3176, `harness/tools/exec_target.rs`, `session/exec_target_launch.rs`, `rsi_common::exec_target`): `LaunchConfig.exec_target` (`Host` default) binds a Harness session's `shell`, `exec_command` and `write_stdin` to one Terminal-Bench task container on a docker host: `scoped_shell_command` runs `docker -H <host> exec -i -w <workdir> [-u <user>] [-e RSI_EXEC_ID=<uuid>] <container> [timeout -k 5 <secs>] bash -c <cmd>` in the same scoped worker unit with an explicit environment (`PATH HOME USER LANG SSH_AUTH_SOCK` plus the ownership stamps) and no `unshare` wrapper. Only daemon code builds a container target; `LaunchSessionParams` and every agent verb have no field for it. `resolve_launch_exec_target` runs before any side effect at the fresh launch, continue, restart resume and both rotation sites and validates live (`exec_target_invalid:<reason>`: host in the operator setting `bench.docker_hosts` (empty refuses all), `docker inspect` running with `com.docker.compose.service=main` and `com.docker.compose.project=<registered project>`, image RepoDigests include a caller-pinned digest); a binding that cannot be read or whose container is gone/unreachable on a continuation refuses `exec_target_unavailable:<reason>`. The binding is the append-only `session_exec_targets` row (V182), resolved through `continued_from`; a container-bound session runs only on the Harness loop (`ToolPolicyGuard::refuse_container` refuses every CLI/Local/Antigravity route, so no fallback to the host). The registry for a container target (`HarnessToolRegistry::container_target_tools`) registers only the plan/context/compact tools, `read_output` and the three container tools (no file tool, `apply_patch`, `git`, `view_image`, web, codegraph, memory, `schedule_wake`, `rsi_control`, MCP); a call that still names a host tool is refused `container_target_host_tool_refused` at every execute entry point, and a completion gate fails closed. The kill guard and the custody guard are skipped for the container target only. `shell` uses the target's per-call ceiling (default 900 s) enforced by `timeout` in the container and by the client (+15 s); cancelling or terminating an `exec_command` session runs the marker-based in-container kill (`RemoteKill`, a `/proc` scan for the session's `RSI_EXEC_ID`), never on a command's own exit. Tests use a fake `docker` shim (`exec_target::test_support::Shim`), never real docker.

### Bench run adapter

Bench run adapter (#3178, `bench/{mod,listener,task,cap,trace}.rs`, `rsid_store::store::bench`, the bench migration, `rsi_common::bench`): a Terminal-Bench trial on the laptop starts, watches and stops exactly one daemon Harness session for its task container, only inside one admitted bench run. `BenchService::open_run` records the run (`bench_runs`: config path/digest, dataset commit, docker host, model, effort, budget, per-task cap, concurrency, pinned task set with each task's image digests) and binds the per-run unix socket `~/.rsi/bench/<run>/adapter.sock` (directory 0700, socket 0600), bound only while the run is `active` and again by `BenchService::restore` after a daemon restart (called in `main` right after `restore_sessions`, before the restart journal claims). The socket serves only `BenchTaskStart`, `BenchTaskStatus`, `BenchTaskCancel`, `BenchTaskFinish` and `BenchTraceRead` (the daemon's line-framed JSON-RPC) for its own run: any other method is `-32601` with data code `bench_method_not_allowed`, the run comes from the socket (parameter types refuse unknown fields, so a request cannot name another run), and these methods are NOT in `AGENT_VERBS`, `READ_VERBS`, a native tool or the daemon socket (the socket is the capability: any same-uid process that can open it is bounded by the run's budget, the grant and container validation). `BenchTaskStart` is idempotent per (run, trial) (the same request answers the stored trial, another request is `bench_trial_conflict`, a refused or failed start leaves no trial except a launch failure, which settles it `cancelled` with `bench_start_failed:<code>`) and checks in order: the run is active and the task is in its pinned set; `allowed_launches` for (OpenRouter, model, effort) via the project grant (`bench_launch_not_allowed`, an empty grant fails closed); the M4 run budget (`BenchHost::run_budget` = `SpendEnforcer::run_budget_report`, its refusal code passed through) and that the remainder minus what live trials may still spend (`cap - spent` each) covers one more per-task cap (`bench_run_budget_insufficient`); the run's concurrency cap (`bench_concurrency_exceeded`, atomic in the claim); then the container target against the operator's `bench.docker_hosts`, the compose labels and the TASK's pinned digests (`exec_target_invalid:<reason>`). It launches an `is_eval`, `skip_context_pipeline` OpenRouter-on-the-Harness-route session with the bench profile (#3177) and the container target in an empty per-trial scratch directory. The per-task USD cap (`bench::cap::BenchTaskGuardedControl`, a `ModelCallControl` wrapper next to M4's `SpendGuardedControl`) refuses a model call when the session's own spend (`Store::bench_session_usage`, the increment SQL, never cumulative rows) plus a reserve reaches the cap (#3350: the reserve is an upper bound on one call, the prompt window at the model's input price plus the loop's largest requested output at its output price, never below the session's largest call or 1% of the cap; a model with no known price is refused `bench_task_cost_unknown`): the session ends `bench_task_budget_exhausted` (monitor stop reason, never healed, the task graded normally). It also refuses a session whose task is no longer `running` (`bench_task_not_running`: cancelled, or resumed after a restart), a completed call of unknown cost (`bench_task_cost_unknown`) and an unwritable trace (`bench_trace_write_failed`). A trace line lost on the FINAL response (no later admission to check) fails that call's completion with the same code after its usage is recorded, and a trial whose trace file lost any line settles with stop reason `bench_trace_write_failed` whatever ended the session (`bench::trace::path_write_failed`, #3349). The cap and trace path ride on `BenchLaunchProfile` (`task_cap_micro_usd`, `trace_path`). The daemon writes `~/.rsi/bench/<run>/<trial>/trace.jsonl` live from the loop ports (`DaemonAdmission` for each model request as handed to the provider and response as returned, `DaemonTools::execute` for each tool call and the result the model saw; no timestamps, so equal transcripts give equal bytes) and records its sha256 at finish; `BenchTraceRead` pages it by byte offset in whole lines. A trial settles when its session ended (on any Status/Finish read): usage from the increments, the `bench_route` audit verdict, the `harness_build_digest` and the trace hash; `BenchTaskCancel` marks the trial `cancelled` first (so the guard stops spending) and then interrupts the session; the daemon also cancels a trial 30 s after its `agent_timeout_sec`. A restart marks every live trial `infra_interrupted` (never resumed, the adapter reads that state); `bench_runs`/`bench_tasks` are never deleted from and a settled task row only moves forward (the migration's triggers). The route audit accepts the launch row's `session.launch.fresh` purpose (the first model call settles the launch admission). A `bench` job (#3181, `agent_jobs/bench.rs`, contract in `docs/agents/rsid-rpc-contracts.md` "Bench jobs") creates the run: it opens it with `BenchService::open_run` (run id = job id, so a restart rebinds the same run), forwards `adapter.sock` to the laptop and joins the Harbor results with the `bench_tasks` rows into `record.json`.

## Providers

### OpenRouter spend ceiling

OpenRouter spend ceiling (#3154, `openrouter_spend.rs`, pure rules in `rsi_common::openrouter_spend`): the operator setting `openrouter_spend_cap_usd` (0 = off, TUI Settings > Cloud Spend, `UpdateDaemonConfig` alone, never in a batch) is ARMED by a fresh probe of the account `total_usage`, recorded with its time as `openrouter_spend_baseline_usd` / `openrouter_spend_armed_at` (derived rows; refused as operator writes; changing an armed cap keeps its baseline, 0 forgets it). Spend = last probed usage (`ProviderStatusService::usage_probe`, refreshed at most once a minute, kept fresh by `run_spend_probe_loop`) + `Store::openrouter_billable_spend_settled_since` (increment SQL, never a raw SUM; counts every `OpenRouter` and `Harness` invocation, the safe direction) - baseline. An armed cap with no probe or one older than 5 minutes FAILS CLOSED (`openrouter_spend_cap_probe_stale`). Billing predicate: `launch_bills_openrouter` (the OpenRouter provider on any route, or Harness with an `openrouter.ai` base URL; a Harness continuation or rotation carries no base URL, so there the model resolves the route the way `resolve_provider` does, e.g. an `openrouter/...` model). A refused model call settles its pending invocation with the refusal's own code (`openrouter_spend_cap_probe_stale` is not recorded as `openrouter_spend_cap_reached`). Tests use a mock `OpenRouterApi`, never the network.

### Provider plan-window outage

Provider plan-window outage (#3066): while a provider's plan window (five-hour, seven-day) is exhausted the manager policy gate refuses with `manager_v2_provider_usage_limit` (`rsid_core::provider_exhaustion::is_usage_window_refusal`; one predicate, `Store::provider_usage_window_hold_until`, latest reset of the exhausted windows, 5 minutes when a window reports none). That refusal names the account, not the wake or node: a scheduled resume refused by it (a parked worker's `when` wake included) is re-armed at the reset through `hold_wake_for_provider_exhaustion`, spends no retry budget, is never escalated or settled, and is delivered when the provider accepts it, so `parked_awaiting_resume` keeps the node `running` for the whole outage. A topology launch refused by it returns the attempt to `Reserved` with one `admission_hold{waiting_on_provider}` event instead of settling `launch_refused`. Account changes observed by the Claude login probe or Codex account poll invalidate old windows (#3568); unchanged or unknown accounts preserve them. `ClearProviderUsageHold` is the operator-only fallback (`<Space>hu` / `:provider-clear-hold`); clearing capacity releases held wakes on the next scheduler pass (also without a manager notice), and Reserved launches retry on the next executor tick.

### Provider CLI contract canary
