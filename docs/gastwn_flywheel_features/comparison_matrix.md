# Feature Comparison Matrix

This matrix maps every Flywheel feature to its closest Gastown equivalent (or None).

> **Note**: For the full ChatDev 2.0 (DevAll) comparison, see the standalone document at `thoughts/shared/research/2026-03-12-chatdev2-flywheel-comparison.md`. A three-system comparison matrix is included there.

| Flywheel Feature                                  | Gastown Feature                               | Equivalence            | Notes                                                                                                                                                                                                                                                                |
| ------------------------------------------------ | --------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session Lifecycle Management                     | Polecats + Convoy + Done                      | Partial                | Flywheel has a TUI state machine (Starting/Running/WaitingApproval/Completed/Failed/Interrupted/Archived) managed by a daemon; Gastown has polecat lifecycle (working/stalled/zombie/nuked) managed by Witness. Flywheel is single-user; Gastown is multi-agent.       |

## ChatDev 2.0 (DevAll) — Third System Addendum

ChatDev 2.0 occupies a fundamentally different architectural layer (computational graph / workflow definition) than either Flywheel (interface) or Gastown (operational orchestration). The following table maps key ChatDev 2.0 capabilities to their Flywheel and Gastown equivalents:

| ChatDev 2.0 Feature | Flywheel Equivalent | Gastown Equivalent | Notes |
|---|---|---|---|
| YAML Workflow Definition | None | TOML Formulas (partial) | ChatDev 2.0 defines full agent topologies in YAML; Gastown Formulas define step sequences. Flywheel has no workflow definition. |
| 8 Node Types (agent, human, subgraph, python, passthrough, literal, loop_counter, loop_timer) | Session (single type) | Agent roles (Mayor, Polecat, Witness, etc.) | ChatDev 2.0 has typed computational nodes; Flywheel has homogeneous sessions; Gastown has role-based agents. |
| Edge Condition System (function, keyword) | None | None | Conditional data routing between graph nodes. Neither Flywheel nor Gastown has conditional inter-session data flow. |
| Dynamic Fan-Out (Map/Tree) | None | None | Edge-level parallel expansion with configurable splitters. Unique to ChatDev 2.0. |
| Cycle Detection (Tarjan SCC) | None | None | Automatic loop detection and iterative execution in graphs. Unique to ChatDev 2.0. |
| Subgraph Composition | None | None | Hierarchical graph nesting via file reference or inline config. Unique to ChatDev 2.0. |
| Three Execution Strategies (DAG, Cycle, Majority Vote) | Session state machine | Formula type dispatch | ChatDev 2.0 auto-selects strategy based on graph topology. |
| Memory Module (simple/file/blackboard + FAISS) | Memory subsystem (FTS5 + vector) | Key-value store (beads kv) | All three have memory; Flywheel's is the most sophisticated (hybrid search, file watcher); ChatDev 2.0's integrates per-node in the graph. |
| Thinking Module (reflection) | None | None | Post-generation LLM reflection pipeline. Unique to ChatDev 2.0. |
| Function Calling + MCP Tools | None (delegated to provider CLI) | Claude Code hooks (tap guard) | ChatDev 2.0 has first-class tool integration with auto-schema. |
| WebSocket Streaming | JSON-RPC 2.0 over Unix socket | None (tmux session direct) | Both ChatDev 2.0 and Flywheel stream execution events; different transport. |
| Batch Execution (CSV/Excel) | None | Convoy parallel dispatch (partial) | ChatDev 2.0 processes CSV/Excel batches; Gastown dispatches convoy bundles. |
| Schema Registry (6 registries) | None (compile-time) | Plugin system | ChatDev 2.0's registry enables zero-code extension; Gastown's plugins need TOML; Flywheel requires Rust code changes. |
| Human-in-the-Loop (WebSocket blocking) | WaitingApproval + a/d keys | Mail escalation | ChatDev 2.0 blocks graph execution at human nodes; Flywheel pauses for tool approval; Gastown sends mail. |
| Vue Web UI + Visual Editor | ratatui TUI | gt feed TUI + htmx dashboard | All three have UIs at different layers of sophistication and purpose. |
| Python Script Execution (python node) | None (sessions run provider CLIs) | None (agents run in tmux) | ChatDev 2.0 runs Python scripts as graph nodes with subprocess isolation. |
| Token Tracking (per-provider JSON export) | Per-turn dual counting + live display | OpenTelemetry + gt costs | Flywheel's tracking is the most granular; ChatDev 2.0 exports at workflow end. |
| Edge Payload Processors (regex, function) | None | None | Transform data as it flows between nodes. Unique to ChatDev 2.0. |
| Config Schema API (breadcrumb navigation) | None | None | Dynamic JSON schema generation from config classes for UI rendering. Unique to ChatDev 2.0. |
